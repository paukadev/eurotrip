# ADR-004: Stack React + Vite + TypeScript, hash routing, JSON validado com zod

## Status

Accepted

## Date

2026-07-22

## Context

O app é um site estático somente-leitura (ADR-001, ADR-002), com uma home e uma página
por destino, roteável por deep link, publicado em hospedagem gratuita e que deve crescer
"aos poucos". Os dados vêm de um único `viagem.json` editado à mão. As user stories
exigem: rotas por destino com deep link e refresh funcionando em host estático
(US-014.EC-1), mensagens de erro legíveis para JSON inválido/incompleto (US-013) e
renderização parcial dos dados válidos.

Precisamos decidir o framework, o modelo de roteamento, a forma de carregar os dados e a
estratégia de validação/tipagem.

## Decision

- **Framework**: React + Vite + TypeScript (SPA client-side). Build estático via
  `vite build`.
- **Roteamento**: `react-router` em modo **hash** (`/#/destino/:slug`). Hash routing
  resolve deep link e refresh em qualquer host estático sem configuração de rewrite.
- **Dados**: um único `public/viagem.json`, **buscado em runtime** via `fetch`, permitindo
  trocar apenas o JSON no deploy e exibir estados de carregando/erro.
- **Validação e tipos**: `zod` valida o JSON no carregamento e **deriva os tipos
  TypeScript** do schema. A validação produz as mensagens legíveis e a renderização
  parcial exigidas por US-013, normalizando defaults (ex.: `status` ausente → `pendente`).
- **Estilo**: CSS Modules (scoped, zero-config no Vite).
- **Testes**: Vitest + React Testing Library (unit/componente) e Playwright (e2e).

## Alternatives Considered

### Alternative 1: Next.js (static export)

- **Description**: React com roteamento por arquivos e SSG.
- **Pros**: Convenções prontas, URLs limpas.
- **Cons**: Mais peso/configuração para um app pequeno sem backend; rotas dinâmicas em
  export estático exigem cuidado extra.
- **Why rejected**: Excede a necessidade; Vite entrega o mesmo com menos cerimônia.

### Alternative 2: History routing (URLs limpas) em vez de hash

- **Description**: `/destino/:slug` com History API.
- **Pros**: URLs mais bonitas.
- **Cons**: Refresh/deep link em host estático exige fallback (404.html/rewrite) que varia
  por provedor.
- **Why rejected**: Hash routing funciona igual em qualquer host gratuito sem config,
  cumprindo US-014.EC-1 sem acoplar a um provedor.

### Alternative 3: Import do JSON em build-time + tipos manuais

- **Description**: `import viagem from './viagem.json'`, tipos escritos à mão.
- **Pros**: Sem fetch nem estados de carregamento.
- **Cons**: JSON malformado quebra o build (sem mensagem em runtime); tipos manuais
  divergem do dado; erros semânticos ainda precisariam de validação.
- **Why rejected**: `fetch` + `zod` cobre erro de runtime, validação semântica e tipos a
  partir de uma só fonte.

## Consequences

### Positive

- Um só schema `zod` gera tipos, validação e mensagens de erro — fonte única.
- Deep links robustos em qualquer host estático.
- Trocar dados = substituir `viagem.json` e republicar.

### Negative

- Hash nas URLs (`/#/...`) é esteticamente menos limpo.
- Uma dependência de validação (`zod`) e uma de roteamento (`react-router`).

### Risks

- Fetch do JSON pode falhar (404/rede). Mitigação: estado de erro dedicado
  (US-013.EC-1).

## Implementation Notes

Camada `loadTrip()` central: fetch → `TripSchema.safeParse` → normalização (defaults,
slugs, ordenação) → objeto tipado consumido via React Context. Ver TechSpec → Core
Interfaces.
