# ADR-001: Dados da viagem em arquivos JSON versionados, editados à mão

## Status

Accepted

## Date

2026-07-22

## Context

O usuário quer controlar os dados da viagem (destinos, datas, hospedagem, translados,
roteiro, itens comprados/pendentes) e declarou explicitamente que os dados serão
"controlados com arquivos JSON". O projeto é pessoal, para uma única pessoa, e a
intenção é "construir aos poucos". Não há requisito de múltiplos usuários editando ao
mesmo tempo, nem de fluxo de autenticação, nem de banco de dados.

A pergunta de fundo é COMO os dados entram no sistema: editados à mão nos arquivos, ou
por formulários dentro do app que gravam os JSON.

## Decision

Os dados vivem em arquivos JSON versionados junto ao código. O usuário edita esses
arquivos à mão. A aplicação é **somente-leitura** sobre esses dados: lê os JSON e os
exibe. Não há telas de edição nem escrita de dados pela interface na versão inicial.

## Alternatives Considered

### Alternative 1: Formulários no app que gravam nos JSON

- **Description**: A interface teria telas de CRUD que escrevem de volta nos arquivos.
- **Pros**: Mais confortável para editar; menos chance de JSON malformado.
- **Cons**: Exige camada de escrita/persistência, validação e — em hospedagem estática
  gratuita — um backend, o que contraria "subir em serviço gratuito" simples.
- **Why rejected**: Adiciona complexidade que o usuário não pediu e conflita com o
  objetivo de começar simples e crescer aos poucos.

### Alternative 2: Banco de dados

- **Description**: Persistir os dados em um banco (SQLite/Postgres/serviço gerenciado).
- **Pros**: Consultas ricas, integridade referencial.
- **Cons**: Requer backend e infraestrutura; excessivo para uma viagem pessoal.
- **Why rejected**: Fora de proporção com o escopo e com o modelo "arquivos JSON".

## Consequences

### Positive

- Máxima simplicidade: sem backend, sem banco, sem autenticação.
- Dados versionados: histórico de mudanças no controle de versão.
- Compatível com hospedagem estática gratuita (ADR-002).

### Negative

- Editar JSON à mão é sujeito a erro de sintaxe; o app precisa falhar de forma clara
  quando o JSON estiver inválido.
- Atualizar dados exige novo deploy/publicação (não é edição em tempo real).

### Risks

- JSON malformado quebra a página. Mitigação: validação na carga e mensagem de erro
  legível indicando o arquivo/campo problemático, sem tela branca.

## Implementation Notes

Definir um schema JSON claro para a viagem e para cada destino (ver PRD → Business
Rules). O formato base parte de `{ name, inicioData, fimData }` por destino, expandido
com hospedagem, translado, roteiro por dia e itens de checklist.
